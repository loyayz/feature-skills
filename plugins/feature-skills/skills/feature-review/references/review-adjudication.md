# 评审候选裁决

reviewer 报告和主代理自审都是候选输入，不是缺陷结论。先核对候选对应的快照身份仍有效，再以当前需求、已固化最终 spec、项目和领域规范、完整 diff 及现实调用链为基线，逐项重新定位和验证。合并相同根因，保留最强证据和反证，不按来源、措辞或数量裁决。

候选只能落入一个结果：

- **confirmed：** 位于当前已授权范围内，并有契约证据、可证逻辑错误或现实可达失败路径。
- **requirements-change-needed：** 与目标存在现实因果关系，但修复必须改变已固化契约本身，包括业务目标、语义、外部契约、权限、安全、事务、一致性、异常、补偿或重要运行影响。停止修改并返回需要重新收敛的变化。恢复已约定的权限、异常或事务行为属于契约内修复，不能仅因实现行为改变而归入本类；契约明确但缺少执行许可时单独报告授权缺口。
- **rejected：** 与当前语义冲突、证据仍是线索、只覆盖理论边界或契约外状态、与目标无因果关系，或者只是替代架构和未来扩展。
- **unresolved：** 缺少一个会改变上述分类的现实事实。该事实可能影响正确性时停止；否则披露为未验证风险。
- **consolidated：** 与更强候选属于同一事实、失败路径和所有权，合并到该候选。

要求新增校验、兜底、清洗、默认值、恢复、重试、`try/catch`、权限限制或对应测试的候选，还必须证明当前层拥有真实边界、触发条件来自允许状态、保护的是已固化结果，并且不会建立第二事实源。无法证明时拒绝；会产生新业务语义时归为 `requirements-change-needed`。

只有 `confirmed` 可以进入已授权修复。基准始终是当前已固化契约，不能以有缺陷的当前行为代替契约。废弃建议不写入需求、spec 或最终交付文档。
