# 最终 Spec

## 目标与边界

理解目标、成功结果、适用对象、触发条件、约束和明确排除项，闭合会改变业务结果的决策，形成一个可直接实施的最终 spec。只做与需求和生产方案存在因果关系的调查；实施批次、构建命令和逐文件实施计划不属于本工作。确认需求所必需的内部对象和调用点可以调查，其事实不自动成为最终设计约束。

不运行编译、测试或工程质量门禁。只使用能回答当前需求问题的只读证据；用户要求的基线验证作为独立工作交回调用者，不以构建结果代替需求证据，也不自行调用其他能力。

## 需求发现

发现顺序固定为：

1. 从原始请求和用户指定文档提取目标、约束、受保护行为与已知路径，不先做仓库范围搜索。
2. 每项调查都对应一个尚未确定的问题，并且不同答案会改变业务结果、需求解释、外部契约、授权范围或最小生产方案。不能说明这种影响时停止调查，把细节留给实现。
3. 需要代码、配置、项目规范或调用点事实时，由主代理决定问题、证据边界和查询方式，只查询能闭合当前问题的最小范围。查询已经收敛为固定命令和固定返回字段时，可按入口定义交给低成本代理；代理不判断证据意义。当前节点证据充分后停止该节点的查询，继续处理由它解锁的下游分支；不能把一个节点已查明当作整棵需求树已闭合，也不为已闭合节点重复取证。
4. 可从用户输入、项目资料、代码和既有约定可靠推断的内容由主代理负责查证和解释，并记录假设。只有无法可靠推断、且多个答案会产生不同业务结果的事项才询问用户；一次合并当前可决定的问题，中性说明选项及各自业务结果，不给推荐答案或预选方案。推荐只在 frontier 闭合后的 owner 方案阶段形成。

用户已经给出精确路径和事实时不为形式追加机械查询。新的实现细节只有在会改变业务方案时才进入未验证项。

范围完整性由本 skill 独立负责。需求涉及全部对象或完整表示时，查明会改变范围、业务结果或最小方案的实际对象与表示；不得凭单一目录、接口或命名约定推断全部覆盖。调查方法按问题选择，不固定矩阵格式或字段。仓库可查事实自行查明，不以 TBD 转成用户决定；范围已充分闭合后停止扩张。需要交接或追溯时才单独保存必要证据，不默认增加调查文档。

## 需求收敛与第一原理方案

以下顺序作为状态机固定执行，不合并或调换步骤。每个状态在进入下一状态前产生一条简短、用户可见的自然语言 checkpoint；加载对应 Skill 不等于状态完成，方案形成后回填先前 checkpoint 也不构成顺序证据。checkpoint 只证明转换条件，不限制问题数量、调查方法、推理深度、方案结构或正文格式；简单任务可以每项一句，复杂任务按实际需要展开。过程 checkpoint 不写入最终 spec，避免形成第二事实源。

### 1. Brainstorming：只理解需求

先使用 `superpowers:brainstorming` 理解目标、约束、业务结果和歧义，但不接受其实施计划或后续执行建议，也不在此时冻结或推荐方案。

完成后先发送 `understanding-ready` checkpoint，至少说明当前目标、约束和仍存在的歧义，并明确尚未形成推荐方案。该 checkpoint 出现前不得提出实现方向、用方案假设驱动源码调查或加载首次 `grilling`。`brainstorming` 在本 skill 中只提供需求理解方法；其普通方案审批门禁不改变本文件的结果分类。

### 2. Grilling：建立需求决策树

完成初步理解后立即使用 `grilling` 深入理解需求：将每个会改变范围、业务结果、外部契约或授权的决定及其下游依赖展开为决策树。主代理逐分支自我追问：有哪些合理选择、各自产生什么结果、现有需求和事实支持哪一个、选择后又解锁哪些问题。按前置条件已确定的 frontier 分轮处理，不能只检查用户明说的歧义或停留在第一层问题。

- 环境事实从项目证据查明，不询问用户。
- 能从已确认需求和事实可靠推出的节点，由主代理比较相关选择后自主决定，明确采用结论及依据；不把可自行决定的分支交回用户。
- 纯技术节点不进入用户 frontier，留给实现按已固化的结果与约束决定。
- 只有无法可靠推断、且多个合理答案会改变业务结果的节点才进入用户 frontier。
- 权限、范围和不可逆影响按本文件的授权门禁处理。

每轮取得新事实、作出有依据的自动决定或收到用户答案后，重算依赖节点和 frontier，继续展开新解锁的分支，直到每个需求相关分支都已处理。前置事实尚在调查或前置决定尚未确定时，下游保持待解锁，不猜测前置答案；其他已就绪分支继续处理。被排除的选择说明排除依据，不继续展开只在该选择成立时才有意义的子树。

自动闭合必须来自用户已确认的需求或查明的事实；证据不足且存在多个合理业务选择时，不能把方案偏好当作自动决策。frontier 为空还须确认没有待解锁的前置问题或静默遗漏的相关分支，才表示需求树闭合。深入处理限于当前需求有实际因果影响的选择，不无限枚举理论场景。业务 frontier 未清空前不得形成推荐方案，也不得用方案后的复核替代本次决策树。

首次 grilling 的用户可见输出简短说明需求理解中的分支处理：用户已明确的结论直接沿用；自动闭合且影响范围或业务结果的分支说明结论及依据；仍待决定的分支中性说明不同选择的业务结果。将这份摘要合并到本轮最小问题或 `frontier-closed` checkpoint，不另设汇报、台账或确认环节；后续轮次只说明新增或改变的结论，不穷举技术节点，也不重复请求确认已有答案。

frontier 非空时返回 `requires-user-decision` 的最小问题并停在本状态。frontier 清空后、形成任何推荐方案前，先发送 `frontier-closed` checkpoint，结合上述分支摘要明确没有剩余业务 frontier。`grilling` 在本 skill 中提供决策树、依赖和 frontier 方法；可推导节点仍必须自动闭合，不因其默认访谈方式而逐项询问用户。其推荐答案习惯及交互工具的推荐/预选惯例不适用于尚未闭合的业务 frontier；工具不能中性呈现时使用自由文本问题。

### 3. Owner：形成第一原理方案

frontier 清空后，由本 skill 的执行者作为 specification owner，从第一原理明确真正业务结果、必须成立的现实约束、已验证事实、薄弱假设和最小生产变化。现有实现只是证据与约束，不是默认方案。每项设计必须形成：

```text
已确认目标或已验证约束 → 业务可观察结果 → 最小生产动作
```

删除某个拟新增或保留的结构后，如果必要复杂度不会重新分散到多个真实所有者或边界，该结构不承担当前必要责任，应从方案删除。未来扩展、可测试性、偏好的分层方式和“更清晰”不能单独证明生产修改必要。

方案形成后发送 `owner-solution-ready@<revision>` checkpoint，简要说明方案如何从已确认目标或现实约束导出。revision 是当前方案内容的局部身份，可使用本次调用内单调递增的短标识；它不要求哈希，也不限制方案表达。frontier 未闭合时不得产生该 checkpoint。

## SSOT、领域与一致性

最终 spec 是需求和生产设计的唯一语义权威。同一业务事实、术语、状态、规则和外部契约只能有一个当前定义；需求文档、旧计划、讨论记录和候选方案不能形成平行事实源。用户纠正或新证据改变结论时直接重写当前 spec，不保留废弃解释或演进叙事。

方案形成后再次使用 `grilling`，并同时使用 `domain-modeling`，复核必要性、领域概念、术语、事实所有者和内部一致性。这是独立的方案后复核，不能代替方案前的需求决策树。已有领域文档时按项目规则同步；不存在时不创建通用 `CONTEXT.md`、通用领域文档或 ADR。Domain 只承担业务不变量与状态转换；入口和基础设施分别承担自己拥有的真实边界。

复核完成后发送 `post-review-passed@<revision>` checkpoint，摘要说明第二次 grilling 与 domain-modeling 的发现、修正或无 finding 结论。该 revision 必须与当前 `owner-solution-ready` 一致；复核导致方案内容变化时先产生新的 owner solution revision，再对新 revision 重新复核，不能沿用旧结论。

新用户输入、仓库证据或评审发现改变需求理解时，从最早受影响的状态重新进入，并使其所有下游 checkpoint 失效；只改变方案而不重开业务 frontier 时，使 owner solution 和 post-review 失效。失效状态不能靠改写标签恢复，必须重新执行相应 pass。

人工改库、契约外返回或正常链路不可达状态只是理论边界，不据此加入校验、清洗、恢复、默认值、重试、`try/catch` 或测试。简单化也不能删除事务、安全、兼容性和外部协议等真实约束。

## 测试行为与 Spec 内容

生产设计只服务生产场景，不为测试便利新增 hook、setter、公开入口、配置开关、依赖抽象或内部状态暴露。只有业务语义变化，或者行为选择变化且产生不同业务可观察结果时，才把相关普通用例需求写入对应业务规则或受保护行为。

最终 spec 只保留当前有效的：

- 业务结果、规则、领域概念和状态转换；
- 对外可观察行为、外部契约和不变量；
- 已授权责任范围和必须遵守的现实约束；
- 受保护行为；
- 查明后会改变业务方案的未验证事实；
- **变更面契约**：允许新增或改变的业务责任、明确不改变的责任、资源或容量影响及未验证项。

内部文件路径、类名、方法名、实现批次、构建和测试命令、测试文件及执行顺序不进入 spec，除非名称本身是外部 API、协议字段、数据库契约或用户明确批准的架构责任边界。

## 结果分类与完成条件

普通、可回滚且处于当前请求授权范围内的生产修改不设置 spec 审批门禁。只有方案包含不可回滚的数据、外部状态或安全影响，或者执行所需权限没有由当前请求提供时，才返回 `requires-user-authorization`，披露具体变更面、影响和可回滚替代后等待授权。只有存在无法从需求和证据可靠推断、且不同答案会改变业务结果的选择时，才返回 `requires-user-decision`。技术实现选择、共同理解确认、风险感受和“让用户看一眼”都不构成这两种状态。

只有同时满足以下条件才完成：

- 没有未解决的业务歧义、授权缺口或逻辑矛盾；
- 所有会改变需求的分支及其下游依赖已逐轮处理，自动闭合、明确排除或由用户决定，没有待解锁的前置问题或静默假设；
- 每项重要设计都可追溯到已确认目标或现实约束；
- SSOT、领域和一致性复核已完成；
- 变更面契约完整，真实授权缺口已经取得明确授权；
- 最终 spec 已按当前状态重写。
- `understanding-ready → frontier-closed → owner-solution-ready@<revision> → post-review-passed@<same-revision>` 已按实际执行顺序产生；不是方案形成后补写的回顾。

满足全部完成条件时，按入口的输出约定保存最终 spec；独立调用未指定路径也使用默认文档路径，不只在聊天中输出。返回 `implementation-ready`、最终 spec 内容及实际保存路径、四个有序 checkpoint 的简短收敛证据，并明确仍会影响实施的未验证事实，然后停止；checkpoint 位于最终 spec 之外。用户明确要求仅聊天输出时遵守该要求并如实说明未保存文件。不得请求用户批准或确认。返回 `requires-user-decision` 或 `requires-user-authorization` 时只请求解决对应的最小未决项，说明其影响；分支摘要用于告知已闭合结论，不把已经闭合的 spec 整体重新送审。新答案或授权到达后按失效规则重算 frontier、重写当前 spec、再次完成方案后复核，再按本节重新分类。

依赖不可用、必需证据无法取得或自身完成条件无法满足且不是业务选择时返回 `blocked`，给出具体事实和继续所需条件。完成判定由本 skill 负责，不让调用者补做需求审查或校验内部步骤。
