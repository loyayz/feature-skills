# 最终 Spec

## 目标与边界

理解目标、成功结果、适用对象、触发条件、约束和明确排除项，闭合会改变业务结果的决策，形成一个可直接实施的最终 spec。只做与需求和生产方案存在因果关系的调查；实施批次、构建命令和逐文件实施计划不属于本工作。确认需求所必需的内部对象和调用点可以调查，其事实不自动成为最终设计约束。

不运行编译、测试或工程质量门禁。只使用能回答当前需求问题的只读证据；用户要求的基线验证作为独立工作交回调用者，不以构建结果代替需求证据，也不自行调用其他能力。

## 需求发现

从原始请求和用户指定文档提取目标、约束、受保护行为与已知路径，不先做仓库范围搜索。后续调查按当前问题选择方法：

- 每项调查都对应尚未确定、且会改变业务结果、需求解释、外部契约、授权范围或最小生产方案的问题；其余细节留给实现。
- 主代理决定证据边界和查询方式，只查询能闭合当前问题的最小范围。固定命令和返回字段的查询可按入口规则下放，证据意义仍由主代理判断。
- 事实充分后停止该节点的查询，继续处理它解锁的下游分支；不重复取证，也不以局部查明代替整体范围闭合。可推断事项由主代理查证、解释并记录假设，用户问题按下述决策树和结果分类处理。

用户已经给出精确路径和事实时不为形式追加机械查询。新的实现细节只有在会改变业务方案时才进入未验证项。

范围完整性由本 skill 独立负责。需求涉及全部对象或完整表示时，查明会改变范围、业务结果或最小方案的实际对象与表示；不得凭单一目录、接口或命名约定推断全部覆盖。调查方法按问题选择，不固定矩阵格式或字段。仓库可查事实自行查明，不以 TBD 转成用户决定；范围已充分闭合后停止扩张。需要交接或追溯时才单独保存必要证据，不默认增加调查文档。

## 需求收敛与第一原理方案

严格依次执行以下四步，不合并、调换、提前或用后一步替代前一步。每步完成后、进入下一步前发送一条简短、用户可见的自然语言 checkpoint；加载 Skill 或事后补写标签不算完成证据。checkpoint 按实际复杂度说明转换条件，不限制调查方法、推理深度或方案表达，也不写入最终 spec。

第 1 步由本 skill 直接完成；后续依赖 Skill 仅提供对应步骤的方法，不引入额外审批、逐项访谈或实施交接，方法正文按入口规则到对应步骤再加载。第 2 步可形成需求决策的推荐答案；生产方案只在第 3 步形成。

### 1. Requirements Understanding：理解需求

先把用户描述的功能、做法或问题还原为要达成的现实结果：谁在什么场景需要发生什么变化，完成后哪些业务可观察结果应当改变，怎样判断成功。用户明确指定的做法和边界保留为约束；不要把请求中的做法直接当作目标，也不要用偏好的方案替换用户的目标。

从原始请求、指定资料和必要的只读证据中区分用户已明确的要求、查明的现状、自己的推断与尚未确定的含义。按需求相关性理解适用对象、触发条件、范围与排除项、外部契约和受保护行为；对可能多义的术语说明当前解释，检查这些信息与目标、成功结果是否相容。不为填满固定清单而提问或搜索，也不用方案假设驱动源码调查。

目标或成功结果无法在不猜测的情况下说清，或者关键表述存在会改变整体理解的矛盾时，先问一个聚焦的澄清问题，结合回答修正理解。能够准确描述需求但仍有多个业务选择时，明确记录待决定点，交由第 2 步展开；此时不比较选择、不作业务决定、不提出推荐方案。

主代理能用自己的话连贯说明目标、成功后的可观察变化，以及适用的约束和保护边界，并能指出哪些内容仍待第 2 步决定，才发送 `understanding-ready`。checkpoint 简短呈现这份理解，区分已确认内容与重要推断，给用户纠正机会；用户纠正后先修正理解和 checkpoint，再进入受影响的后续步骤。发送前不加载首次 `grilling`。

### 2. Requirements Decision Resolution：闭合需求决策

发送 `understanding-ready` 后立即使用 `grilling`，将会改变范围、业务结果、外部契约或授权的决定及下游依赖展开为决策树。frontier 是前置条件已确定、当前无需猜测即可处理的决策集合。每轮处理整个 frontier，逐节点比较合理选项、业务结果和推荐答案，再用第 1 步确认的目标、约束和查明的事实检验推荐，覆盖静默分支及下游依赖。`grilling` 的逐题交由用户决定规则在本步骤改为自主处理；只有无法可靠推断的业务决定才提交用户。

- 环境事实从项目证据查明，不询问用户。
- 推荐答案是待检验的候选结论。能从已确认需求和事实可靠推出的节点，由主代理自主选定最合适的答案，明确采用结论、依据和排除其他业务结果的原因。
- 纯技术节点不进入需求决策树，留给实现按已固化的结果与约束决定。
- 无法可靠推断且不同答案会改变业务结果的节点停下来请用户决定，中性说明选项及影响，不附推荐或预选；授权缺口和其他阻塞按结果分类处理。

每轮取得新事实、作出有依据的自动决定或收到用户答案后，重算依赖节点和 frontier，继续展开新解锁的分支，直到每个需求相关分支都已处理。前置事实尚在调查或前置决定尚未确定时，下游保持待解锁，不猜测前置答案；其他已就绪分支继续处理。被排除的选择说明排除依据，不继续展开只在该选择成立时才有意义的子树。

frontier 为空且没有待解锁的前置问题或遗漏的相关分支，才表示需求树闭合。自动决定须有已确认需求或查明事实支持，不能用方案偏好弥补证据不足，也不无限枚举与当前需求无因果关系的理论场景。

分支摘要合并到本轮最小问题或完成 checkpoint：沿用用户已明确的结论，说明影响范围或业务结果的自动决定及依据，中性呈现待决定分支的选择和结果。后续只说明新增或改变的结论，不另设汇报、台账或确认环节。

需要用户决定时停在本步骤，按结果分类提问。需求树闭合时发送 `frontier-closed`，以分支摘要说明闭合依据，再进入方案设计步骤。

### 3. Solution Design：形成第一原理方案

以 `frontier-closed` 为前提，本 skill 的执行者作为 specification owner，先从使用者视角说明当前问题与预期的业务可观察结果，再从第一原理明确必须成立的现实约束、已验证事实、薄弱假设和最小生产变化。现有领域文档、ADR、原型和实现须核对适用性与当前效力；仍有效的部分作为证据与约束，不把既有方案当作默认方案。每项设计必须形成：

```text
已确认目标或已验证约束 → 业务可观察结果 → 最小生产动作
```

删除某个拟新增或保留的结构后，如果必要复杂度不会重新分散到多个真实所有者或边界，该结构不承担当前必要责任，应从方案删除。未来扩展、可测试性、偏好的分层方式和“更清晰”不能单独证明生产修改必要。

形成方案时同步收敛当前 spec：逐项核对旧方案、历史规则及其引用是否仍由已闭合需求和当前方案支持。已被取代的内容直接删除，重写受影响章节，使每个业务事实只保留一个有效定义；仍成立的约束和受保护行为继续保留，不因清理历史而丢失。

方案形成后发送 `solution-ready@<revision>`，说明方案如何从目标或约束导出。revision 标识当前方案内容，可用本次调用内递增的短标识，不要求哈希。

### 4. Solution Review：复核方案

最终 spec 是需求和生产设计的唯一语义权威。同一业务事实、术语、状态、规则和外部契约只能有一个当前定义；需求文档、旧计划、讨论记录和候选方案不能形成平行事实源。复核时检查旧方案、历史规则及其引用是否残留；发现已被取代的定义就删除并修正相关章节，不以附录、对照表或演进叙事保留第二套规则。用户纠正或新证据改变结论时直接重写当前 spec，只保留仍有效的设计和真实约束。

对 `solution-ready` 标识的同一版方案再次使用 `grilling`，以具体场景、后果和反例挑战每项生产变化的必要性及遗漏分支；同时使用 `domain-modeling` 检查领域概念、术语、状态、不变量、事实所有者和责任边界的一致性。发现需求理解或业务决定有误时返回受影响的前置步骤；仅方案有误时返回第 3 步形成新 revision，再复核新方案。已有领域文档时按项目规则同步；不存在时不创建通用 `CONTEXT.md`、通用领域文档或 ADR。Domain 只承担业务不变量与状态转换；入口和基础设施分别承担自己拥有的真实边界。

复核完成后发送 `post-review-passed@<revision>`，摘要说明第二次 grilling 与 domain-modeling 的发现、修正或无 finding 结论；revision 必须与当前 `solution-ready` 一致。

人工改库、契约外返回或正常链路不可达状态只是理论边界，不据此加入校验、清洗、恢复、默认值、重试、`try/catch` 或测试。简单化也不能删除事务、安全、兼容性和外部协议等真实约束。

## 变化与失效

用户输入、仓库证据、授权或复核发现改变已有结论时，从最早受影响的步骤继续，该步骤及下游 checkpoint 失效。只改变方案时从第 3 步产生新 revision，再复核新方案；改变需求理解时重新处理受影响的需求树及依赖分支。重新执行后产生有效 checkpoint，不能仅改标签或沿用旧复核结论；最终 spec 随当前结论重写。

## 测试行为与 Spec 内容

生产设计只服务生产场景，不为测试便利新增 hook、setter、公开入口、配置开关、依赖抽象或内部状态暴露。只有业务语义变化，或者行为选择变化且产生不同业务可观察结果时，才把相关普通用例需求写入对应业务规则或受保护行为。

最终 spec 只保留当前有效的：

- 业务结果、规则、领域概念和状态转换；
- 对外可观察行为、外部契约和不变量；
- 已授权责任范围和必须遵守的现实约束；
- 受保护行为；
- 查明后会改变业务方案的未验证事实；
- **变更面契约**：允许新增或改变的业务责任、明确不改变的责任、资源或容量影响及未验证项。

内部文件路径、类名、方法名、实现批次、构建和测试命令、测试文件及执行顺序不进入 spec，除非名称本身是外部 API、协议字段、数据库契约或用户明确批准的架构责任边界。

## 结果分类与完成条件

普通、可回滚且处于当前请求授权范围内的修改不设置 spec 审批门禁。技术实现选择、共同理解确认、风险感受和“让用户看一眼”都不构成暂停理由。需要暂停时由本 skill 独立分类：

- `requires-user-decision`：无法从需求和证据可靠推断，且不同答案会改变业务结果。合并当前可决定的最小问题，中性说明选项和结果，不给推荐或预选方案；工具无法中性呈现时使用自由文本。已闭合结论只告知，不重新请求确认。
- `requires-user-authorization`：方案包含不可回滚的数据、外部状态或安全影响，或者执行权限尚未提供。披露具体变更面、影响和可回滚替代，只请求解决实际授权缺口。
- `blocked`：依赖不可用、必需证据无法取得或完成条件无法满足，且不是上述业务决定或授权问题。给出具体事实和继续所需条件。

获得新答案、授权或证据后，按变化与失效规则继续，再判断完成状态；不把已闭合的 spec 整体送审。

只有同时满足以下条件才完成：

- 没有未解决的业务歧义、授权缺口或逻辑矛盾；
- 需求树按第 2 步的闭合条件处理完成；
- 每项重要设计都可追溯到已确认目标或现实约束；
- SSOT、领域和一致性复核已完成；
- 变更面契约完整，最终 spec 只保留当前有效内容；
- 四个有序 checkpoint 均有效，方案与复核 revision 一致。

满足全部条件时，按入口约定保存最终 spec，返回 `implementation-ready`、最终内容及实际路径、四步的简短收敛证据和仍影响实施的未验证事实，然后停止。用户明确要求仅聊天输出时说明未保存文件；其余情况遵守入口默认路径或调用者指定路径。完成判定由本 skill 负责，不请求整体审批，也不让调用者补做需求审查或校验内部步骤。
